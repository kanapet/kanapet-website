# 独立站维护工作流

本 skill 定义本项目所有网站维护任务的标准流程。用户不是技术人员，请严格按本流程执行，不要要求用户做任何命令行操作。

## 第一步：建立工作环境（每次任务必做）

1. 按项目档案中的仓库地址 clone 代码；若本地已有副本，先 `git pull` 确保是最新版本。
2. 依次读取三份知识文件建立背景（按需读取，不要一次全读）：
   - `SITE-BRIEF.md` —— 品牌、产品目录、页面清单（涉及内容/文案时必读）
   - `CONVENTIONS.md` —— 技术栈、目录结构、部署方式（涉及代码改动时必读）
   - `SEO-STATE.md` —— 优化进度台账（涉及 SEO/GEO 或需要了解历史时必读）
3. 若任何一份文件缺失，告知用户并提议补建，不要凭空假设项目背景。

## 第二步：先给方案，等确认

- 动手修改之前，先输出简短方案：改哪些文件、改成什么、预计影响。
- 方案获得用户明确同意后才执行修改。
- 批量任务（如多个产品页）先改 2-3 个样本给用户看，认可后再批量完成。

## 第三步：执行修改

- 遵守 `CONVENTIONS.md` 中的技术约定。
- 小步修改，保持每次改动聚焦本次任务，不要顺手改无关内容。
- 涉及 SEO 的改动（标题、描述、结构化数据）遵循 Toprank 类审计工具给出的优先级建议。

## 第四步：收尾（每个任务结束时必做）

1. 在独立分支保存改动并完成测试，向用户展示可审查 diff/草稿 PR。
2. 用户明确批准上线后：
   - 将本次改动追加记录到 `SEO-STATE.md`（日期、做了什么、下一步）
   - 合并或推送到 `main`（说明写清本次任务）
   - push 后用 curl 检查网站线上是否正常，异常立即报告
3. 用户说"存档但先不上线"时，push 到草稿分支，不触发上线；用户说"上线草稿"时再合并主分支。

## 特殊指令

- **"退回上一个版本"**：`git revert` 最近一次提交，确认线上恢复正常。
- **"只看进度"**：只读 `SEO-STATE.md` 汇报，不修改任何文件。
- **"继续上次"**：读 `SEO-STATE.md` 最后一条记录，从"下一步"接续执行。

## 红线

- 任何修改先方案后动手，永远不跳过用户确认直接 push。
- 每次任务结束应保存到独立分支；提交审查不等于批准上线，不得自动推送或合并 `main`。
- 不主动碰 Cloudflare 后台；部署依赖 push 自动触发。
